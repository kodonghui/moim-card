# 06 API 계약 체크포인트 (구현 전 계약 검토)

2026-11-28 · 상태: **통과**(질문 1 DEC-023, 질문 2 DEC-024, 질문 3 DEC-025, 승인 버전 PR #8 커밋 `f1e2c43`) · 대상: [api/openapi.yaml](../../api/openapi.yaml)(API-001~016, 오류 코드 22개), 설명 [api.md](api.md)

- **답하는 사람:** 이 단계는 DDD(01)·목업(09)이 아니라서 NEXUS 확정 없이 오랑이의 위임 답으로 통과를 기록해요(DEC-014). 아래 질문 세 개 모두 01 도메인 설계를 바꾸지 않아요.
- **답하는 법:** 질문마다 "추천대로" 또는 번호만 주시면 돼요. 아무 답이 없으면 승인으로 보지 않아요. 질문 1에 답해도 질문 2·3은 답한 것이 아니에요.
- **비교 기준 커밋:** 04 승인 main `6b9d609`. 06의 이전 승인과 이전 계약은 없어요(첫 계약, 깨지는 변경 0개).
- **05와의 관계:** 이 계약은 05 스키마(TBL-001~015)를 따라요. 05 질문 1이 2번(고칠 테이블 있음)이면 이 계약도 고쳐서 다시 물어요.

## 1. 앞서 승인된 것 중 이번 작업이 바꾸거나 빠뜨리는 것

**빠뜨린 것: 없어요.** 서버가 필요한 SPEC 29행은 operation이나 서버 안 작업에 연결되고, 나머지 10행은 서버가 필요 없어요(api.md 3절). 04 행의 고침(C-5, SPEC-002, SPEC-018, SPEC-024, SPEC-025)은 [05 체크포인트 1절](../05-erd/checkpoint-05.md)에 있고 DEC-016·020으로 답이 있어요.

**계약을 쓰다 찾은 것 두 가지:** 승인된 문장끼리, 또는 승인된 문장과 화면이 필요한 것이 부딪혀요. 각각 질문으로 물어요. 질문 2·3의 답(DEC-024, DEC-025)으로 SPEC-025·026·039와 계약의 `Open:` 표시를 고쳤어요.

| 승인 항목 | 승인된 문장 | 부딪히는 점 | 질문 |
| --- | --- | --- | --- |
| REQ-058, SPEC-026 [동시성] | REQ-058: "알림을 신청한 참여자에게만 같은 방의 다른 참여자가 응답을 마쳤을 때 알려야 해요." SPEC-026: "마감과 발송이 겹치면 마감 커밋 뒤의 발송은 신청이 없어 보내지 않음." | 인원의 마지막 사람이 답하면 그 응답과 같은 트랜잭션에서 방이 마감되고 알림 신청이 지워져요(SPEC-015, SPEC-026). 발송은 커밋 뒤에 하므로, SPEC-026 문장을 글자대로 읽으면 **가장 기다린 마지막 응답의 알림이 가지 않아요.** REQ-058은 이때도 알려야 한다고 읽혀요. | 질문 2 |
| SPEC-039 [노출] | "닉네임·누가 답했는지·방 코드 없음" | 목록에서 방을 고르면 그 방의 API(API-004·006·009)를 불러야 하는데, 방 API는 방 코드로 방을 가리켜요. 목록 응답에 방 코드가 없으면 화면이 방을 열 수 없어요. 참여자는 이미 그 방 코드를 가진 사람이에요(초대 링크로 들어왔거나 만든 사람). | 질문 3 |

## 2. AI가 정한 것 (되돌리기 쉬움)

질문 없이 AI가 정했어요. 바꾸고 싶으면 번호로 말해 주세요. 오류와 성공의 경계 R-1~R-11은 [api.md 5절](api.md#5-오류와-성공의-경계-dec-021)에 있고 DEC-021로 기록했어요. 그 밖의 것:

| P-1 | 경로는 `/v1/…`, 요청 ID 헤더 이름은 `Idempotency-Key`(UUID). | 널리 쓰는 이름이에요. 버전을 경로에 둬 다음 계약과 나란히 둘 수 있어요 |

## 3. 체크포인트 질문

**질문 1. API 계약 16개 operation(API-001~016)과 응답·오류 코드를 구현 기준으로 승인할까요?** (DDD 변경 아님. 질문 2·3에 걸린 부분은 답에 따라 고쳐서 승인) — 답: 추천안 1 (DEC-023). R-1~R-11과 P-1~P-6도 함께 승인(DEC-021)

1. 승인해요. 화면은 목 서버로, 서버는 계약 테스트로 이 계약에 맞춰요. **← 추천**
2. 고칠 operation이나 응답이 있어요(API 번호와 고칠 점을 알려 주세요).

- 추천 이유: 모든 operation이 SPEC과 TBL을 가리키고, 응답 표(성공, 400, 401, 403, 404, 409, default)의 각 칸을 응답으로 두거나 이유를 적었어요. 응답 예시 200개가 스키마에 맞고, 오류 코드와 상태가 목록과 같고, 요청 필드의 한계가 05 열의 한계와 같아요(`scripts/check-contract.py` 통과 1095, 실패 0). Prism 목 서버와 Schemathesis가 계약을 읽었어요.
- 반대 근거: 실제 서버로 계약 테스트를 돌린 것이 아니에요. 목 서버는 설계상 대부분을 통과하므로, 서버가 계약과 다른 점은 11 개발 단계에서야 나와요. 또 토스 콘솔에서 사업자 없이 mTLS 인증서가 발급되는지(F-1)를 아직 보지 못했어요. 막히면 API-001과 API-011의 교환 방식을 바꿔야 해요.

**질문 2. 인원의 마지막 사람이 답해 방이 마감될 때, 알림 신청자에게 알림을 보낼까요?** (REQ-058, SPEC-025, SPEC-026 → API-007. DDD 변경 아님: 01 CTX-006의 두 정책 "응답 제출됨 → 알림 보내기", "방 마감됨 → 알림 신청 지우기"의 순서만 정해요) — 답: 추천안 1 (DEC-024). SPEC-025에 문장을 더하고 SPEC-026 [동시성]을 좁혔어요

1. 보내요. 마지막 응답을 저장하는 같은 트랜잭션에서 신청을 지우기 전에 읽어 두고, 커밋 뒤에 그 암호문을 메모리에서만 복호화해 보내요. 식별키는 저장하지 않아요. SPEC-025 주 동작에 이 문장을 더하고, SPEC-026 [동시성]은 "다른 요청이 보내는 발송"으로 좁혀 적어요. **← 추천**
2. 보내지 않아요. SPEC-026 문장 그대로예요. 마지막 응답의 알림은 가지 않고, 신청자는 미니앱을 다시 열어야 최종 카드를 알아요.

- 추천 이유: 신청자가 가장 기다리는 알림은 "모두 답해 카드가 완성됨"이에요. REQ-058은 마지막 응답을 빼지 않아요. 신청과 암호문은 그대로 마감 트랜잭션에서 지워지므로 DEC-019("방이 끝나면 바로 지움")를 지켜요.
- 반대 근거: 복호화한 식별키가 방이 마감된 뒤 몇 초 동안 Worker 메모리에 있어요. 또 템플릿 문구 "친구가 답을 마쳤어요."는 마감을 알리지 않아, 카드 완성을 알리려면 템플릿을 하나 더 검수받아야 해요(1번이어도 첫 버전은 같은 템플릿을 써요).

**질문 3. 내 방 목록(API-012) 응답에 방 코드를 넣을까요?** (SPEC-039 [노출] → API-012. DDD 변경 아님) — 답: 추천안 1, 조건 "방 코드를 기기 로그에 남기지 않음" (DEC-025). SPEC-039 [노출]과 API-012 설명에 반영했어요

1. 넣어요. 화면에는 방 코드를 보이지 않고(SPEC-039 [노출]을 화면 기준으로 읽음), 화면이 방 API를 부르는 데만 써요. SPEC-039 [노출]에 "화면에"를 더해요. **← 추천**
2. 넣지 않아요. 목록에 따로 만든 번호를 주고, 그 번호로 방을 여는 API를 하나 더 둬요(API-017). 그 API도 결국 방 코드를 돌려줘야 화면이 공유 링크(SPEC-022)를 만들 수 있어요.

- 추천 이유: 목록의 방은 모두 내가 이미 들어간 방이라 나는 그 방 코드를 이미 가졌어요(초대 링크, 방 만들기 응답). 넣지 않아도 지켜지는 것이 없고 API만 하나 늘어요.
- 반대 근거: 응답 본문이 기기 로그나 화면 캡처 도구에 남으면 방 코드가 함께 남아요. 마감된 방은 코드만 있으면 누구나 최종 카드를 보므로(DEC-013), 응답에 코드가 나오는 곳을 줄이는 편이 더 조심스러워요.
