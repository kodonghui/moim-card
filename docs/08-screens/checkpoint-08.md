## 1. 앞서 승인된 것 중 이번 작업이 바꾸거나 빠뜨리는 것

**빠뜨린 것: 없어요.** 화면이 부르는 API 16개(API-001~016 전부)의 모든 응답(상태 코드와 오류 코드)이 화면의 상태로 이어지고, 화면에 걸리는 SPEC은 모두 어느 화면 정의에 있어요. 화면이 없는 SPEC 7개는 이유와 함께 [README 3절](README.md#3-화면이-없는-spec)에 있어요(`scripts/check-screens.py` 통과).

**바꾸는 것 하나(질문 2, 추천안 1로 정함 DEC-029):**

| 승인 항목 | 승인된 문장 | 바꾸자는 점 | 이유 | 질문 |
| --- | --- | --- | --- | --- |
| FL-012 "지워졌어요 안내"(DEC-015) | "처음 화면으로 돌아가요. 다시 쓰면 새 사용자로 시작해요." | 자동으로 처음 화면에 가지 않고, "지웠어요" 화면에서 [미니앱 닫기]와 [처음 화면으로] 중 고르게 해요 | 처음 화면(SCR-001)은 열리자마자 사용자 확인(API-001)을 하므로, 자동으로 가면 지운 직후 같은 사람의 사용자 ID가 곧바로 새로 생겨요. "다시 쓰면 새 사용자"라는 문장과도 어긋나요 | 질문 2 |

## 4. 체크포인트 질문

**질문 1. 화면 정의 15개(상태 70개, 공통 처리 G-1~G-10)를 구현과 09 목업의 기준으로 승인할까요?** (DDD 변경 아님. 질문 2에 걸린 SCR-013은 답에 따라 고쳐서 승인) — 답: 추천안 1 (DEC-028). W-1~W-12와 G-1~G-10도 함께 승인(DEC-026). 함께 온 요청: 09 목업 때 방장 화면의 버튼 수와 문구 길이를 사용자님과 같이 봐요([09 준비](../09-mockup/prep.md))

1. 승인해요. 09 목업은 이 상태들을 그리고, 11 개발은 화면 코드를 바꾸기 전에 이 정의를 먼저 고쳐요. **← 추천**
2. 고칠 화면이나 상태가 있어요(SCR·상태 ID와 고칠 점을 알려 주세요).

- 추천 이유: 화면이 부르는 모든 응답이 사용자가 보는 상태로 이어지고(빠진 응답 0), 오류마다 06 계약의 문구와 화면 할 일을 그대로 써요. 목 서버(`prism mock api/openapi.yaml`)로 상태마다 응답을 골라 받을 수 있어 서버 없이 화면을 만들고 볼 수 있어요.
- 반대 근거: 와이어프레임은 회색 그림이라 문구 길이, 버튼 수, 한 화면에 든 정보량이 실제로 괜찮은지는 09 목업에서 눌러 봐야 알아요. 또 AI가 눈으로 본 프레임은 70개 중 4개뿐이에요.

**질문 2. 내 데이터를 지운 뒤 처음 화면으로 자동으로 보낼까요?** (FL-012 "지워졌어요 안내" → SCR-013#done. DDD 변경 아님: CTX-004의 "내 데이터 삭제됨" 뒤 화면만 정해요) — 답: 추천안 1 (DEC-029). FL-012 "지워졌어요 안내" 문장과 SCR-013 규칙에 반영했어요

1. 자동으로 보내지 않아요. "지웠어요"와 "다시 쓰면 새 사용자로 시작해요" 아래 [미니앱 닫기](주 버튼)와 [처음 화면으로]를 두고, [처음 화면으로]를 누를 때만 사용자 확인을 해요. 이 화면은 기록을 바꿔 끼워 뒤로가기가 미니앱을 닫아요. FL-012 단계 문장을 "처음 화면으로 갈지 고르게 해요"로 고쳐요. **← 추천**
2. 승인된 문장대로 자동으로 처음 화면으로 보내요. 지운 직후 새 사용자 ID가 만들어져요(빈 사용자, 식별키 해시와 내부 ID만).

- 추천 이유: 지우기를 누른 사람은 대개 그만 쓰려는 사람이에요. 자동으로 가면 지운 바로 다음 순간 식별키 해시가 서버에 다시 저장돼, "지웠는데 다시 생겼다"는 일이 생겨요. 1번은 다시 쓸 때만 새 사용자가 생겨 REQ-043과 FL-012의 "다시 쓰면 새 사용자로 시작해요"에 더 맞아요.
- 반대 근거: 승인된 흐름 문장을 바꾸고, 계속 쓰려는 사람은 한 번 더 눌러야 해요. 2번이어도 새로 생기는 행에는 응답·닉네임이 없어 개인 정보가 거의 없고, 만들어진 빈 사용자는 그대로 서버에 남아요(빈 사용자를 지우는 정리 작업은 없어요).
