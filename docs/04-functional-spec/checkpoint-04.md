# 04 기능 명세 체크포인트 (명세 고정)

2026-11-28 · 상태: **질문 1·2 답함**(DEC-016, DEC-017), 질문 3 답 대기(사용자님께 여쭘) · 대상: [spec.md](spec.md)(SPEC-001~038, 공통 규칙 C-1~C-10)

- **답하는 사람:** 이 단계는 DDD(01)·목업(09)이 아니라서 NEXUS 확정 없이, 오랑이의 위임 답으로 통과를 기록해요(DEC-014). 다만 질문 3의 1번은 01 도메인 설계의 승인된 규칙을 바꿔요. 02 질문 4(DEC-013)처럼 위임 밖일 수 있어요. 토링이가 판단해 주세요.
- **답하는 법:** 질문마다 "추천대로" 또는 번호만 주시면 돼요. 아무 답이 없으면 승인으로 보지 않아요. 질문 1에 답해도 질문 2·3은 답한 것이 아니에요.
- **비교 기준 커밋:** 02 승인 main `20d6423`(DEC-014). 03은 같은 PR에서 체크포인트 대기예요. 이 단계의 첫 체크포인트라 04의 이전 승인은 없어요.
- **고정의 뜻:** 질문 1이 통과하면 명세가 첫 버전 기준으로 고정돼요. 고정된 행을 나중에 바꾸려면 사용자님(또는 위임) 결정이 필요해요.

## 1. 앞서 승인된 것 중 이번 작업이 바꾸거나 빠뜨리는 것

명세 초안은 승인된 요구사항을 빠뜨리지 않아요(spec.md 6절: REQ 82/82, FL 15/15, 기능 Must 중 SPEC 없는 것 0개). 다만 아래 두 가지는 승인된 문장과 부딪혀 각각 질문으로 물어요. 답이 없으면 승인된 그대로 남고, 걸린 행 4개(SPEC-002, SPEC-024~026)는 `질문 대기`예요.

| 승인 항목 | 승인된 문장 | 부딪히는 점 | 질문 |
| --- | --- | --- | --- |
| REQ-041 | "클라이언트가 사용자를 밝히는 요청을 보내면, 서버는 클라이언트가 보낸 식별키를 그대로 믿지 않고 인증 코드(`User.createAnonymousKeyAuthCode`)를 토스 파트너 API로 교환해 확인해야 해요." | 글자대로면 요청마다 코드를 교환해요. 코드는 5분 안에 한 번만 쓰이고(F-6), 토스 API 한도는 사용자당 분당 20건이에요(REQ-069). 카드를 몇 번 새로고침하면 한도에 닿고, 요청마다 토스 왕복이 더해져 2초 반응(REQ-067)이 빠듯해요. | 질문 2 |

## 3. 체크포인트 질문

**질문 1. 기능 명세 38행(SPEC-001~038)과 공통 규칙(C-1~C-10)을 첫 버전 기준으로 고정할까요?** (질문 2·3에 걸린 4행은 답에 따라 고쳐서 고정해요) — 답: 추천안 1 (DEC-016)

1. 고정해요. 05 ERD와 06 API는 이 명세를 따라요. **← 추천**
2. 고칠 행이 있어요(SPEC 번호와 고칠 점을 알려 주세요).

- 추천 이유: 82개 요구사항이 모두 행에 연결되고, 모든 행에 예외와 Given·When·Then 인수 조건이 있어요. 동시성(동시 입장·제출·마감), 반복(다시 보낸 요청), 노출(카드에 이름 없음, 링크에 방 코드만)을 행마다 적어 05·06·12가 같은 경우를 쓸 수 있어요.
- 반대 근거: 확인하지 못한 사실이 4개 남아 있어요(F-1 인증서 발급, F-2 전환 이벤트, F-3 문항 세트 배포 방식, F-5~F-7은 검색 요약만 봄). 06 API에서 본문을 읽고 결과가 다르면 SPEC-002, SPEC-018, SPEC-020, SPEC-024, SPEC-031·032를 고쳐야 하고, 고정 뒤라 그때 다시 결정이 필요해요.

**질문 2. 인증 코드 교환을 언제 할까요?** (REQ-041 → SPEC-002, C-1) — 답: 추천안 1 (DEC-017)

1. 미니앱을 열 때 한 번 교환하고, 서버가 자기 세션 토큰(무작위 256비트, D1에는 해시만, 수명 12시간)을 발급해요. 그 뒤 요청은 이 토큰으로 확인하고, 토큰이 끝나면 다시 교환해요. 내 데이터 지우기 때 토큰을 없애요. REQ-041의 "식별키를 그대로 믿지 않는다"는 그대로 지켜요. **← 추천**
2. 사용자를 밝히는 요청마다 화면이 새 인증 코드를 받아 서버가 교환해요(REQ-041 글자 그대로).

- 추천 이유: 토스 API 한도(사용자당 분당 20건)에 닿지 않고, 요청마다 토스 왕복이 없어 2초 반응(REQ-067)을 지키기 쉬워요. 서버가 확인한 뒤 발급한 토큰이라 클라이언트가 보낸 값을 믿는 것이 아니에요.
- 반대 근거: 지켜야 할 비밀(세션 토큰)이 하나 늘어요. 토큰이 새면 12시간 동안 그 사람인 척할 수 있어요. REQ-041의 글자("요청을 보내면 … 교환해 확인")와 다르게 읽는 것이라, 1번이면 REQ-041 비고에 "확인은 세션 시작 때"를 적어야 해요.

**질문 3. 기능성 알림을 보낼 식별키를 어떻게 할까요?** (REQ-058, REQ-074, 01 CTX-004 → SPEC-024~026) — 답 대기(01을 바꾸는 질문이라 사용자님께 여쭘)

1. 알림 신청에만 식별키를 암호화해(AES-GCM, 키는 Workers 비밀 값) 두고, 방이 마감·만료되거나 신청자가 데이터를 지우면 바로 지워요(길어야 30일). REQ-074와 01 CTX-004 규칙에 "알림 신청이 있는 동안만 암호화해 둠" 예외를 적어요. 01 문장은 목업 단계 때 01 domain.md 후속 고침과 함께 사용자님 확인을 받아요. **← 추천**
2. 기능성 알림을 첫 버전에서 빼요. REQ-058~061을 `deferred`로 두고 DEC-012를 바꿔요. REQ-074와 01 규칙은 그대로예요.
3. 알림을 넣되 식별키를 두지 않고, 신청한 사람이 미니앱을 연 동안에만 화면 안 알림으로 보여 줘요(토스 푸시가 아님).

- 추천 이유: DEC-012가 고른 "친구가 답을 마쳤어요" 알림을 지키면서, 식별키를 두는 곳을 알림 신청 하나로, 기간을 방이 열린 동안으로 좁혀요. 토스 정책 노트도 식별키 같은 민감 정보는 암호화하고 서비스 종료 때 파기하라고 해요(02 출처, 토스 5절).
- 반대 근거: 되돌릴 수 있는 식별키가 서버에 생겨, 비밀 값과 D1이 함께 새면 신청자의 식별키가 드러나요. 승인된 01 규칙을 바꾸므로 사용자님 확인이 필요해요. 2번이면 바꿀 문장이 없고 출시 준비(템플릿 검수, 동의문, 발송용 mTLS)도 줄어요. 3번은 앱을 닫은 사람에게 닿지 않아 알림의 쓸모가 작아요.
